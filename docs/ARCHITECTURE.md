# Архитектура проекта

## Почему не используются ES Modules

При прямом открытии `index.html` через `file://` браузеры, особенно Safari, могут блокировать загрузку локальных ES Modules из-за CORS. Поэтому проект разделён на обычные deferred scripts. Это сохраняет простоту запуска без Node.js и сервера.

## Поток приложения

1. `core/runtime.js` создаёт общие ссылки на DOM, константы и состояние.
2. Файлы `model/` нормализуют стены и блоки крыши, включая геометрию конька, скаты и правила допустимых пересечений.
3. Геометрические файлы определяют физические границы стен и алгоритмы привязки.
4. Editor-файлы реализуют инструменты: рисование, фигуры, ластик, выбор, перемещение, ресайз и раздельную историю слоёв.
5. Canvas-файлы отвечают за систему координат, масштаб и отрисовку.
6. Feature-файлы реализуют подложку, JSON и автосохранение.
7. `app/events.js` связывает DOM, клавиатуру и Canvas с функциями редактора.
8. `app/bootstrap.js` восстанавливает состояние и запускает первый render.

## Состояние

Общее состояние хранится в глобальной lexical environment обычных script-файлов. Такой подход выбран осознанно ради совместимости с `file://`. Не объявляйте повторно существующие `let`/`const` имена в других файлах.

Состояние плана разделено на коллекции `walls` и `roofs`. Выделение общее, но всегда относится к активному слою. Undo/Redo и очистка работают отдельно для слоёв стен и крыши.

## Модель крыши

`assets/js/model/roofs.js` владеет форматом блока крыши и чистой геометрической логикой. Блок хранит прямоугольные границы, стадию строительства, тип (`multi`, `single`, `concrete`), поворот и свойства двух концов конька. Для многоскатной крыши `Rotation` задаёт положение начала конька: `0` — сверху, `90` — справа, `180` — снизу, `270` — слева. UI и Canvas не должны самостоятельно определять допустимость пересечения.

Многоскатные блоки также образуют иерархию через внутренние поля `IsRoot` и `ParentId`. Root может быть только один, не имеет parent и обязателен для экспорта JSON только при наличии хотя бы одной многоскатной крыши. Пока root назначен, другие блоки не могут получить этот признак: сначала его нужно снять с текущего root-блока. Каждый многоскатный блок, не являющийся root, обязан ссылаться через parent на любой другой существующий блок крыши. У таких дочерних блоков скат в начале конька всегда неизменяемый, а его маркер и popup не отображаются. Бетонные блоки не могут быть root, но также обязаны иметь `ParentId`; односкатные блоки в иерархии не участвуют. Во внешнем JSON эти свойства называются `Root` и `Parent`; импорт также принимает прежние внутренние имена. Нормализация иерархии выполняется через `normalizeRoofHierarchy()` после импорта, восстановления истории, удаления и дублирования, а обязательность parent проверяется через `roofHierarchyIssue()`.

Пересечение блоков по умолчанию запрещено. Исключение рассчитывает `roofOverlapAllowed()`: оба блока должны быть многоскатными, их коньки должны быть параллельны, а меньший блок обязан совпадать с одним поперечным краем большого и входить в него допустимым образом. Все операции изменения геометрии должны проверять итоговую коллекцию через `findInvalidRoofOverlap()` до записи состояния.

`assets/js/editor/roofs.js` отвечает за создание, перемещение с шагом 10 мм, клавиатурное перемещение, ресайз, поворот и popup свойств скатов. `assets/js/canvas/renderer.js` только отображает модель: полупрозрачные блоки, коньки, маркеры и разрешённые зоны пересечения.

`assets/js/features/roof-image-export.js` скачивает в папку загрузок архив `house_plan_with_images.zip`. Внутри находятся JSON и подпапка `images`: на каждый изменяемый скат многоскатной крыши формируется отдельное изображение серого шаблона стен с узлами и одной направленной стрелкой; дополнительно формируется шаблон `walls_black.png`, где обычные стены чёрные, а веранды красные. Пути к PNG записываются в свойства соответствующих скатов. `SlopeStart` дочерней многоскатной крыши во внешний JSON не передаётся.

## История и хранение

`assets/js/editor/history.js` содержит два независимых стека: `walls` и `roof`. Любое изменение должно вызывать `commitHistory()` при корректном `activeLayer`. Импорт переинициализирует оба стека.

JSON и autosave хранят обе коллекции. Нормализация импортированных данных выполняется через `createWall()` и `createRoof()`; при добавлении полей модели следует сохранять обратную совместимость со старыми данными.

## Декларативные действия HTML

В HTML больше нет встроенных `onclick`. Кнопки используют:

- `data-mode="draw-normal"` для переключения режима;
- `data-action="export-json"` для команды;
- дополнительные `data-factor` и `data-value` для параметров.

Все команды зарегистрированы в `bindUiActions()`.
